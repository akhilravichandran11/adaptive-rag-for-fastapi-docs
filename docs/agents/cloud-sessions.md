# Cloud and worktree sessions

Agents also run outside the main checkout: in cloud sessions (Claude Code on
the web, Cursor and Codex cloud agents) and in new local worktrees. This doc
sets the local and cloud rules side by side, then covers setup and the cloud
detail for commits, `.scratch/` and Linear.

## Local and cloud, side by side

| | Local checkout | Cloud session |
|---|---|---|
| Where the work lands | the main checkout, which other chats share along with its git index | the session's own branch (`claude/…`, `codex/…`, `cursor/…`) and a draft pull request on each repository |
| Commits and staging | agents never stage or commit; the lead hands the user the `git add` line and the message | the agent commits and pushes to its branch early and often; `main` changes only through a pull request the user merges |
| Claiming a ticket | `ticket.py claim` after the user's yes | move the Linear issue to In Progress, then `ticket.py claim --write` on the scratch branch |
| Approving record edits | the proposal page, then yes in chat; a `ticket.py` flip needs only the yes | the draft pull request on the scratch repository is the approval |
| Step 8 reviews | `code-review` and `tdd` are user-level skills on the Mac, not in the repo | those two skills are not installed. When step 8 calls for a Spec review, the lead runs it as one spawned subagent that is given the ticket; a Standards review, which runs only when the user asks for it, is also given `docs/conventions.md`, `docs/simplification-conventions.md` and the open-question list. Neither uses the tool's built-in review of the same name. Tests are written first, by hand |
| Showing work to the user | the visual tools ([`visual-tools.md`](visual-tools.md)) | the pull request conversation and line comments, or "Review in Linear" |
| Paid or live steps | a single supervised chat | never. Cloud environments are set up with no paid keys |
| Views (`NOW.md`, `views/`) | regenerated by `now.py` | left alone; the user regenerates them after merging |
| Process notes and the handback | in the lead's report, sent to the process-lead chat | in the handback, which rides in the scratch pull request; a process problem also gets one comment on the Linear issue |
| Closing a ticket | `ticket.py close` on the user's "committed" yes | not in the cloud session. After the user merges, the next local chat closes it with the merge commit |
| Guards | the pre-commit hooks run, among them the reserved-words hook, which checks staged file content against the list in `.git/info/reserved-words`; the progress hook runs after each reply. No hook checks commit messages or pull request text | the same pre-commit hooks run. `session_setup.sh` copies the reserved-words list from the scratch clone; a session without the scratch repo has no list, and that hook passes silently. There is no progress hook. As locally, nothing checks commit messages or pull request text |

## Tools that exist only on the Mac

A cloud session has the repository's files and nothing from the user's home
folder. Each row names a tool installed only on the Mac and what a cloud
session does instead.

| Tool | Named in | In a cloud session |
|---|---|---|
| `code-review`, `tdd` | [`issue-tracker.md`](issue-tracker.md), steps 7 and 8 | the Step 8 row above |
| `to-tickets`, `implement`, `grilling`, `grill-with-docs`, `wayfinder` | [`issue-tracker.md`](issue-tracker.md), Workflow | not installed, and the user starts most of them. Planning and ticketing stay in a local chat; a cloud session implements a ready ticket through its tool's batch-lead file |
| The plan judge, `scripts/judge_plan.sh` | `AGENTS.md` | it runs the other tool's CLI (`codex` for a Claude plan, `claude` for a Codex plan), which a cloud session lacks. Write "judge not run" in the scratch pull request; the user runs the judge locally before approving, or writes "skip the judge" |
| Plannotator and the proposal-page builder, `crit`, `grill-with-ui`, `visual-plan`, `visual-recap` | [`visual-tools.md`](visual-tools.md) | local pages; the Approving and Showing work rows above |
| `visual-explainer`, `archify`, `diagram-design` | [`visual-tools.md`](visual-tools.md) | not installed; a diagram goes in the pull request as Mermaid or a committed SVG |
| The reserved-words list | the Guards row | copied from the scratch clone by `session_setup.sh` |
| The progress and view hooks | the Guards and Views rows | user-level on the Mac; none in the cloud |
| Agent teams in a terminal | `CLAUDE.md` | terminal only; the batch lead's named subagents work in a cloud session |

Claude Code reads skills from `.claude/skills/`, and Codex and Cursor read
`.agents/skills/`; the skills that git excludes reach no cloud session.

## Setup

`scripts/session_setup.sh` prepares a checkout: it links `.scratch`, runs
`uv sync --locked --extra dev`, downloads the local models and installs the
pre-commit hooks (a worktree shares the main checkout's). It finds the repo
from its own path, so it runs from any directory. It stops at once in the main
checkout, the only one with a real `.scratch` folder, and is safe to run
again. A step that fails prints a `session_setup:` line saying what to rerun.

| Session | What runs the script |
|---|---|
| Claude with one repository, cloud or worktree | the SessionStart hook in `.claude/settings.json` |
| Claude cloud with two repositories | the cloud environment's setup script (`bash <code repo>/scripts/session_setup.sh`), since a session with two repositories reads only the plugin keys of `.claude/settings.json`: its hooks, `env` and permission rules, including the deny rules on pushing to `main`, don't apply |
| Cursor cloud | `install` in `.cursor/environment.json` |
| Cursor worktree | `.cursor/worktrees.json` |
| Codex cloud or worktree | the environment setup script in Codex's settings |

`.scratch` then points at:

- **in a worktree,** the main checkout's `.scratch`, so every session edits the
  one live copy;
- **in the cloud,** a clone of the private scratch repo
  (`adaptive-rag-for-fastapi-docs-scratch`) beside the code repo. Claude and
  Codex attach it as a second repository; Cursor clones it with the access
  `repositoryDependencies` grants. A Claude session with only the code repo
  attached cannot reach the scratch repo, so it has no `.scratch`.

## Commits in the cloud

Commit and push to the branch your tool created (`claude/…`, `cursor/…`,
`codex/…`), then open a draft pull request with the Linear issue ID in its
title. `main` changes only through a pull request the user merges. If your
tool cannot push or open the pull request itself, say so in your final
message. The local no-commit rule in `CLAUDE.md` exists because local chats
share one git index; a cloud session has its own. Claude's cloud harness
pushes the session branch whenever it reaches a stopping point, and no
setting turns that off; that fits the rule above, so let it push.

## Scratch in the cloud

1. Update the clone before reading it: `git -C .scratch pull --ff-only`. If
   `.scratch` is missing, work from the Linear issue and say so in the pull
   request.
2. Make scratch edits on a branch with the same name as your code branch, push
   it, and open a draft pull request on the scratch repo. That pull request is
   the review: it stands in for the proposal page and the "yes" in chat
   ([`visual-tools.md`](visual-tools.md)).
3. Leave `NOW.md` and `views/` to the user, who regenerates them after merging.

## Linear

Move an issue to In Progress before you start work on it: that status is the
claim other sessions see, so pick an issue nobody has claimed. Sign each
comment with your tool: `[Claude Code]`, `[Cursor]` or `[Codex]`.
